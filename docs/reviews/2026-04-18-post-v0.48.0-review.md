## Commit d1e85da — `feat(admin): global session kill panic button`

Files: `app/admin_ui.py`, `app/observability.py`, `app/templates/ops.html`,
`tests/test_global_session_kill.py`, `CHANGELOG.md`.

### Findings

**MEDIUM — caller-session-preservation relies on non-empty `SESSION_COOKIE`**

`admin_kill_all_sessions` computes `current_fp = _fingerprint(request.cookies.get(SESSION_COOKIE, ""))`.
If the cookie header is somehow missing on the POST (browser quirk, proxy
strip, misconfigured gateway), the fingerprint collapses to
`sha256("").hexdigest()` — a fixed constant. The subsequent
`AdminSession.fingerprint != current_fp` check still excludes exactly one
synthetic row (the empty-cookie row if one exists), but effectively kills
the caller's own session too because their real fingerprint no longer
matches. The handler still succeeds, emits audit, and redirects — but the
303 response means the next request lands on a revoked session and the
operator is immediately logged out mid-incident.

`admin_kill_other_sessions` has the identical pattern, so this is not a new
regression — but a guard like
`if not request.cookies.get(SESSION_COOKIE): return _redirect(..., "error", ...)`
on both handlers would harden against a surprising behavior gap in the
operator-safety story (emergency button shouldn't log the operator out).
Concrete suggestion:

```python
signed = request.cookies.get(SESSION_COOKIE, "")
if not signed:
    return _redirect("/admin/ops", "error",
                     "No active session cookie — refusing to mass-revoke")
current_fp = _fingerprint(signed)
```

**LOW — `datetime.now(timezone.utc)` written into naive `DateTime` column**

`AdminSession.revoked_at` is declared as a naive `DateTime` (no `timezone=True`),
but the handler writes `datetime.now(timezone.utc)` (aware). SQLAlchemy
silently strips tzinfo on most backends but raises on PostgreSQL with
`TIMESTAMP WITHOUT TIME ZONE` in strict mode. The existing
`admin_kill_other_sessions` has the same pattern so this is pre-existing,
not a regression. The PAT code uses the belt-and-braces
`.replace(tzinfo=None)` pattern — would be nice to standardize. No action
required for this commit.

**LOW — test assertion `after_audit == before_audit` in `test_unauth_post_is_rejected`**

Line 140 of the test does `assert _count_audit("admin.global_session_kill") == _count_audit("admin.global_session_kill")`
which is a tautology (and comment acknowledges this). Test still covers
the main bounce-status assertion so functionally fine, but the audit-delta
bit is dead weight — remove or rewrite as pre-call / post-call snapshot.

**INFO — token-version bump uses `Account.token_version + 1` SQL expression**

Good: runs as a single atomic UPDATE, no read-modify-write race. This is
the right call and worth calling out as correct concurrency handling.

**INFO — CSRF gate, confirmation phrase, caller-session preservation all tested.**
Pattern conformance with `admin_kill_other_sessions` is tight. CHANGELOG
accurately reflects code. Audit detail payload is bounded (two integers,
no PII). Observability allowlist entry added.

## Commit e9dfbd9 — `feat(admin): webhook delivery manual retry button`

Files: `app/admin_ui.py`, `app/observability.py`,
`app/templates/webhook_deliveries.html`, `tests/test_webhook_retry.py`,
`CHANGELOG.md`.

### Findings

**MEDIUM — retry re-dispatches through the same prefix-allowlist gate**

`_webhooks.fire()` checks `_matches(event.get("action", ""), prefixes)` and
silently drops if the current `GlobalPolicy.webhook_event_prefixes` no
longer covers `row.event_action`. This means an operator who narrows the
allowlist after the original delivery fails will find the "Retry" button
appears to succeed (303, flash "Retry enqueued", audit row lands) but
zero network traffic leaves the box. The audit event still records
`webhook.retried` without any outcome field.

Not wrong, but misleading. Concrete mitigation: either (a) skip the prefix
gate for manual retries (pass a flag into `fire()`), or (b) surface a
"filtered by prefix" note in the flash. A code-level hint in the handler
docstring would at least warn readers:

```python
# Note: _webhooks.fire() applies the current prefix allowlist.
# If the operator has narrowed webhook_event_prefixes since the
# original delivery, this retry silently no-ops.
```

**LOW — null `event_action` falls through as empty string**

`"action": row.event_action or ""` — if the seeded row has `NULL`
event_action, `_matches("", prefixes)` always returns False, so retry
no-ops. Not a correctness bug (audit row is still honest), but test
coverage skips this branch. Would be an 8-line additional test.

**LOW — test mixes authenticated session state across tests**

`test_retry_success_emits_audit_and_new_delivery` calls
`webhooks.drain(timeout=5.0)` then `webhooks._reset_pool_for_tests()`
inside a single test. If two tests in the same module enqueued webhooks
concurrently (not currently the case here, but module-scoped
`_bootstrap_db` means tests share DB state), the drain could block on a
prior test's still-pending submission. Given the current test set
serializes cleanly this is latent — worth documenting as a test-ordering
constraint if more webhook tests are added.

**INFO — CSRF via `dependencies=[Depends(require_csrf)]` correctly applied.**
403 on missing CSRF verified by dedicated test. 404 as flash-redirect
(not an HTTP 404 body) matches the established admin handler pattern.

**INFO — audit.emit wrapped in try/except — matches `revoke_all` pattern**
in `api_pats.py`; swallows emit failure so webhook retry outcome is
reported to the operator regardless of DB transient on the audit row.

**INFO — observability allowlist entry added; CHANGELOG accurate.**

## Commit 90510dd — `feat(pats): atomic rotation endpoint with pat.rotated audit action`

Files: `app/api_pats.py`, `app/pats.py`, `app/observability.py`,
`app/__init__.py`, `tests/test_pat_rotation.py`, `CHANGELOG.md`,
`docs/plans/2026-04-18-pat-rotation-plan.md`.

### Findings

**MEDIUM — expiry carry-over re-attaches `tzinfo=UTC` only on read, writes naive**

`rotate()` reads `old.expires_at` (stored naive in the DB), does
`old.expires_at.replace(tzinfo=timezone.utc)` to synthesize an aware
datetime, then hands it to `issue()` which does `.replace(tzinfo=None)`
again. Round-trips through aware/naive with the assumption that the
persisted naive value was already UTC. This is the codebase's
established convention but if the DB ever held a local-tz naive value
(e.g., migrated from a legacy schema), the carry-over would be off by the
offset. Not a new regression — `issue()` already does this — but worth a
docstring note on `expires_at` that naive = UTC is load-bearing.
Concrete test gap: assert that a PAT issued with a ~12h TTL, then rotated
12h later (mocked clock), still expires at the original absolute timestamp
within 1s.

**LOW — race between `old.revoked_at` assignment and `issue()` flush**

`rotate()` sets `old.revoked_at = now`, then calls `issue()` which does
`db.flush()`. Both writes land in the same transaction (the `get_session`
dep commits after the handler returns) — so atomicity is correct. But if
`issue()` raised between the assignment and flush, the caller would see
the old token's revoke persisted while the new one isn't minted. In
practice `issue()` only raises on bcrypt/DB errors which would also fail
the final commit and rollback both — so the atomicity story holds.
Verified by code read only, not by test; a "`issue` raises mid-rotate
leaves old token live" regression test would be overkill.

**LOW — `ip_allowlist_count` in audit detail can mislead**

`detail={"ip_allowlist_count": len(row.ip_allowlist) if row.ip_allowlist else 0}`.
`row.ip_allowlist` is a JSON list — an empty list `[]` would pass the
truthy guard as falsy and log 0, which is technically correct but visually
ambiguous vs. "never configured" (None). Minor — audit forensics rarely
care about the 0-vs-None distinction.

**INFO — audit.emit wrapped in try/except.**
Matches the `revoke_all` pattern; `create_token` and `revoke_token` in
the same module do NOT wrap, so there is an inconsistency within
api_pats.py. Rotate picked the safer (swallow) option. Worth a follow-up
pass to decide whether all PAT lifecycle audit emits should swallow or
propagate uniformly — not blocking.

**INFO — tests cover**
- success path (new ≠ old, attributes carried)
- audit event + detail payload
- 404 on foreign token (authorization enforced)
- 404 on already-revoked token
- allowlist membership
- TTL carry-over (`delta < 2s` absolute timestamp assertion — good)
No 401-for-missing-auth test, but that's `get_current_account` machinery
tested elsewhere.

**INFO — CHANGELOG accurate; plan doc present.**
